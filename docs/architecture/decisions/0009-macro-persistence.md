# ADR 0009: Persistent, editable macros (no execution)

- Status: implemented as software (IPC version 5 `ListMacros`/`GetMacro`/`SaveMacro`/`DeleteMacro`, a `peripheral-hub-macros` crate with SQLite persistence, daemon validation/CLI and a desktop editor); simulated evidence only, no physical or hardware-compatibility claim, and **no macro execution**.
- Date: 2026-10-16.

## Context

The master document's §4.6 lists macros as a domain feature (the user's "Fase 5"; the master's own Fase 5 is the out-of-scope DRA). The desktop already had a pure-TypeScript macro *draft* (validate/serialize/simulate) that was never persisted and never reached the daemon, and the SDK models `MacroCapabilities` but no stored macro contract. The remaining §4.6 gap recorded after multi-zone lighting was "macro persistence/limits in the daemon". Persisting and executing macros are different risks: storage/editing is safe and useful, while execution would require capturing or injecting input. SDK 1.0/Core/Registry contracts, the profile schema version and the declarative manifest schema must not change, and the MVP explicitly forbids global input injection.

## Decisions

1. Add a dedicated `peripheral-hub-macros` crate with a bounded, versioned model: `MacroId` (validated token), `KeyPress { down, up, tap }`, `MacroAction` (`key`/`delay`), `MacroRepeat { times, interval_ms }`, `Macro { id, name, actions, repeat, profile }`, `MacroSummary` and a `MacroFile` envelope (`macro_schema_version = 1`). Symbolic key names are stored; no captured input is modeled, so keystroke logging is impossible.
2. Enforce limits before any persistence, import or export: `MAX_MACRO_ACTIONS = 4096`, `MAX_MACRO_NAME = 64`, `MAX_DELAY_MS = 60000`, `MAX_MACRO_REPEAT = 1000`, `MAX_MACRO_INTERVAL_MS = 60000`, `MAX_MACRO_ITERATION_MS = 600000` and `MAX_MACRO_TOTAL_MS = 3600000`. Repetition is always finite; `validate()` rejects malformed names, non-token keys, empty/oversized action lists, out-of-range repeats/pauses and over-long durations.
3. Persist through the existing storage crate using `MacroRepository` (`open`, `open_in_memory`, `open_file`, `save`, `get`, `list`, `delete`) and **its own forward-only migration stream at version 1**. Because the storage `Database` tracks a single global `pragma user_version`, macros use a **separate `macros.sqlite` file**; sharing the profile file would collide two `v1` migration streams.
4. Bump the wire contract to `IPC_VERSION = 5` with `ListMacros`, `GetMacro`, `SaveMacro` and `DeleteMacro`, `Reply::Macros`/`Reply::Macro`, and `Fault::Macro(MacroFault)` (`Invalid`, `UnsupportedVersion`, `NotFound`, `Storage`). The `SaveMacro` payload is the validated `Macro` (wire key `macro`; the Rust field is `macro_value` because `macro` is a reserved keyword). Older clients are rejected by the existing incompatible-version path.
5. The daemon validates the macro and, when `profile` is set, confirms the referenced **stored profile exists** before writing (otherwise `Fault::Macro(Invalid)`). Persisting a macro never opens a device, touches a transport or executes the macro. The optional profile link is advisory metadata only.
6. Surface it through existing layers only: the daemon CLI gains `macros`/`macro-get`/`macro-save`/`macro-delete`/`macro-export`/`macro-import` and a `--macros PATH` serve flag, and the desktop Macros screen lists, edits, validates, imports/exports and persists macros through the restricted Tauri bridge. The frontend still performs no device/transport access and the dry-run simulation remains a descriptive trace.

## Consequences

Macros are now modeled and persisted end to end — bounded DTO, validated storage, versioned IPC, daemon CLI and desktop editing/listing — with unit/integration tests over in-memory and temporary-file stores and local IPC doubles (validation and limits, JSON round-trip, invalid/future import, CRUD, file-backed persistence across reopen, reject-before-write, profile-link existence, and IPC round-trip). **Execution is deliberately absent:** stored macros are never run, injected or hooked, and the CLI/screen state this explicitly. Button binding is not modeled; the only link is an advisory profile reference. The IPC version bump requires the frontend mirror (`apps/desktop/src/types/ipc.ts`) to move to 5 in lockstep. The subsequent §4.6 display contract/preview increment is recorded in ADR 0010.
